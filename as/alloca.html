1What is alloca?

alloca(n) = memory on the stack. It is not a real function call.
The compiler turns it into a few instructions, and the important one is sub rsp, size.

The stack grows down. So "make space" just means "move rsp down". The bytes between the new rsp and the old one now belong to the function. When the function returns, rsp goes back up, and the space is gone. You never call free().

2Where does 0x260 come from? Try any size

I compiled alloca(n) for many n. The constant in add rax, … is always n + 8: alloca(1) → 0x9, alloca(600) → 0x260, alloca(601) → 0x261. gcc adds 8 bytes of slack so it can always align the returned pointer to 16. Then the run-time code rounds up to a multiple of 16, because rsp must stay 16-byte aligned (an ABI rule).

3Using the pointer, and what -O2 does

In main.c the result of alloca is thrown away. Real code keeps it: char *p = alloca(600);. Then gcc adds 4 instructions after sub rsp to make p 16-byte aligned. Here rsp is already aligned, so p = rsp.

char *p = alloca(600); at -O0 (after the same size math):
sub rsp, rax ; the allocation mov rax, rsp add rax, 0xf ; + 15 shr rax, 0x4 ; ÷ 16 (drop rest) shl rax, 0x4 ; × 16 mov QWORD PTR [rbp-0x8], rax ; p = (rsp + 15) & ~15
gcc -O2 main.c, the whole main:
main: mov eax, 0x7b ret ; The memory is never used, ; so the optimizer deletes alloca. ; No push rbp, no sub rsp. Nothing.

Takeaways

  • alloca(n) = size = round_up_16(n + 8), then sub rsp, size. No call, no heap.
  • The memory is between the new rsp (the bottom, p[0]) and rbp.
  • leave (= mov rsp, rbp + pop rbp) frees it in one move. That is why a function with alloca always keeps rbp as a frame pointer.
  • RE pattern: sub rsp, <register> mid-function, often with the add 0xf / shr 4 / shl 4 alignment trick → alloca, or a C99 variable-length array (VLA).
