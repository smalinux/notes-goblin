Short answer. The bytes have no separators. The CPU knows only where an instruction starts: the address in RIP. It reads the first byte, and the opcode says which fields follow and how big they are (ModRM? SIB? displacement? immediate?). Add the sizes, and you have the length: next RIP = RIP + length. Every boundary after that follows from the first one. Start at the wrong byte, and you get a different instruction stream that still looks valid.

Only the opcode is always there (dashed = optional). Each field tells the decoder whether the next field exists, and how big it is. An instruction can be at most 15 bytes. A longer one raises a general-protection fault (#GP).

2The decoder's algorithm, for one instruction

0
Start at RIP

The entry point, or the target of a jump / call / ret. That address is the only thing the CPU "knows".

▼
1
Is this byte a prefix?

66, 67, F0, F2, F3, 2E, 36, 3E, 26, 64, 65. If yes: take it, and look at the next byte. 66 changes the immediate size (imm32 → imm16); 67 changes the address / displacement size.

▼
2
REX (40–4F)? VEX (C4, C5)? EVEX (62)?

REX.W can turn some imm32 into imm64: mov r64, imm64 = 48 B8 + 8 bytes.

▼
3
Read the opcode, look it up in the opcode map

0F = go to the 2-byte map; 0F 38 / 0F 3A = 3-byte maps. Each entry says: "has ModRM?" and "immediate size?".

▼
4
ModRM? Read it and split the bits

mod (2 bits) and r/m (3 bits) decide if a SIB byte follows and how big the displacement is.

▼
5
SIB, if mod ≠ 11 and r/m = 100

If SIB.base = 101 and mod = 00, a disp32 follows.

▼
6
Displacement

mod = 00 → none (but r/m = 101 → disp32, RIP-relative) · mod = 01 → disp8 · mod = 10 → disp32 · mod = 11 → register, none.

▼
7
Immediate, of the size the opcode said

Done. length = sum of all fields, and next RIP = RIP + length.

3Why this matters for reverse engineering

x86 code is not self-synchronizing. Nothing in a byte says "I am the first byte of an instruction". You saw it in the stepper: start one byte late, and the b8 that was an opcode becomes a ModRM byte, the zeros that were an immediate become a displacement, and the instruction even eats the first byte of the next one.

objdump from +0:
0: 31 c0 xor eax,eax 2: b8 00 00 00 00 mov eax,0x0 7: 05 .byte 0x5
objdump from +1, same bytes:
1: c0 b8 00 00 00 00 05 sar BYTE PTR [rax+0x0],0x5
  • Overlapping instructions / anti-disassembly: code can jump into the middle of another instruction on purpose. Both decodings are real, and both run.
  • Linear sweep (objdump) decodes byte after byte. Data inside code can push it off the right boundaries, and it may stay wrong for a few instructions.
  • Recursive descent (IDA, Ghidra, Binary Ninja) starts at known entry points and follows jumps and calls, the same way the CPU does. That is why it is harder to fool.

4How the hardware does it fast

Decoding byte by byte is serial and slow. Real cores split the work into stages:

FetchTake an aligned 16–32 byte block from the L1 instruction cache, at the predicted RIP.
Length decodeCompute a length at every byte offset in parallel, then chain them from the known start and mark the boundaries.
Instruction queueHolds the instructions, now split apart.
DecodersSeveral decoders turn x86 instructions into µops.
µop cacheKeeps already-decoded µops by address, so hot loops skip length decoding.
  • AMD cores have stored boundary bits in the L1 instruction cache, next to the bytes, so each cache line is length-decoded only once.
  • A 66 prefix on an opcode with an imm32 changes the length: a length-changing prefix (LCP). Intel decoders need a slow path of several cycles for it, a known performance trap.
  • Branch prediction gives the next start address, so the front-end knows where the next chain of boundaries begins.

Try it yourself

$ printf '\x31\xc0\xb8\0\0\0\0\x05' > b.bin $ objdump -D -b binary -m i386:x86-64 -M intel b.bin # start at +0 $ objdump -D -b binary -m i386:x86-64 -M intel --start-address=1 b.bin # start at +1

Takeaways

  • The CPU finds the end of an instruction by decoding it: prefixes → opcode → (ModRM → SIB → displacement) → immediate.
  • The opcode decides if there is a ModRM byte and how big the immediate is; ModRM decides SIB and displacement.
  • Only the first boundary is known (RIP). A wrong start gives a different, valid-looking stream.
