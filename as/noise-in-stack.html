Noise in stack — f2() prints f1()'s locals

RE4B p.73 · 1.9.4 · gcc -O0 -fcf-protection=none · x86-64 · ASLR off · values taken from a real gdb run
$ ./a.out 1, 2, 3 ← f2 never set a, b, c

C source

void f1() { int a=1, b=2, c=3; // written, never used }; void f2() { int a, b, c; // uninitialized! printf ("%d, %d, %d\n", a, b, c); }; int main() { f1(); f2(); };

Same caller, same depth → same rbp (d670). Only the return address changed (518a → 5194). f2's a, b, c land on f1's leftovers.

why it lines up exactly

Both functions are called from main with the same rsp, both do push rbp; mov rbp,rsp, and both declare three ints in the same order, so gcc gives them the same slots: a=[rbp-0xc], b=[rbp-0x8], c=[rbp-0x4].

That's luck, not a rule. Change the order, add a variable, call something between f1 and f2, or build with -O2 and you get different garbage — that's the "noise" RE4B means. Reading an uninitialized local is undefined behaviour in C.

takeaways

  • Returning from a function doesn't clean its stack — it only moves rsp up.
  • The next call at the same depth reuses the same bytes, so uninitialized locals show the previous callee's values.
  • f1 needs no sub rsp because it's a leaf (red zone); f2 calls printf, so it must reserve its frame.
  • Security angle: this is how info leaks happen (leftover pointers / canaries / secrets in uninitialized stack vars).
