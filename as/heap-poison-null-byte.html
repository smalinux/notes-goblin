Poison NULL Byte

One byte. Always 0x00. Always just past the end of a heap buffer. That is enough to make glibc believe a chunk is shorter than it is — and from a disagreement about size you get overlapping chunks, which is a write into an object that is still alive.

1 The bug class the most boring bug in C, weaponised

A poison NULL byte is an off-by-one heap overflow whose single overflowing byte is a zero terminator. You do not choose the value, you do not choose the offset, and you get exactly one byte. It is the smallest heap corruption that still ends in a shell — which is why it is a classic.

In a heap buffer, “one past the end” is not unused slack. It is glibc’s own bookkeeping — and, on 64-bit little-endian, it is specifically the least significant byte of the next chunk’s size field. The allocator laid its metadata exactly where your loop went one step too far.

2 Chunk anatomy why index == usable_size hits the size field

glibc stores a chunk header inline, immediately before the pointer it hands you. Two qwords: prev_size and size. The pointer you get (mem) is chunk + 16. The size field counts the whole chunk including the header and is always a multiple of 16, so its low 4 bits are free for flags:

A malloc(0x500) request becomes a 0x510-byte chunk, of which 0x508 bytes are usable — the extra 8 are the next chunk’s prev_size slot, which is dead space while you are alive. So mem[0x508] is the first byte of the next chunk’s size.

Requests whose remainder makes usable == req + 8 are the comfortable ones (0x100, 0x500…): a one-past-the-end write at buf[usable] lands precisely on the size byte. With other request sizes the slack moves the landing spot — this is why heap exploits are written against specific allocation sizes, and why attackers groom the heap to get those sizes.

3 What one NUL buys a lie about where a chunk ends

Writing 0x00 over the low byte of size does two things at once:

effectmechanicsconsequence
shrink0x511 → 0x500: the size is rounded down to a multiple of 0x100glibc now believes the chunk ends up to 0xf0 bytes earlier than it does. The real neighbour’s prev_size is never updated, so the two records disagree.
clear PREV_INUSEbit 0 of size goes to 0the previous chunk is now declared free. On free() of this chunk, glibc will walk backwards by prev_size and try to merge — using a number the attacker may control.
The phantom boundary is the whole attack: glibc will place the next chunk header 0x10 bytes before the real one — inside memory the attacker already owns, where a convincing fake header can be waiting.

4 The attack chain from a size lie to overlapping chunks

  1. Groom. Allocate a, b, c adjacent, sizes chosen so the off-by-one lands on b.size’s LSB and so b bypasses tcache (above 0x410) and lands in the unsorted bin.
  2. Plant. Still inside b’s own data, write a fake chunk header at b_chunk + 0x500, the address the phantom boundary will point to. This is just data from b’s point of view.
  3. Free b. Now c.prev_size records 0x510 and c’s P bit is 0.
  4. Poison. a[usable] = 0 shrinks b.size to 0x500.
  5. Re-allocate. Ask for memory that fits in 0x500. glibc carves the shrunken b, checks its (forged) phantom neighbour, and hands b back — while c still believes the chunk before it starts 0x510 bytes back and is free.
  6. Collapse. Free c. glibc sees P=0, reads prev_size = 0x510, walks back to b and merges — swallowing allocations that are still live into one big free chunk.
  7. Cash out. The next malloc of that size returns a pointer that overlaps a live object.
Overlapping chunks turn a one-byte bug into a controlled write into a structure the program still trusts — the standard pivot to a __free_hook-style target, a vtable, or a tcache fd.

5 Lab on glibc 2.39 three programs, real output

Step 1 — see the byte land and watch glibc notice

// poison.c — gcc -O0 -o poison poison.c
#include <stdio.h>
#include <stdlib.h>
#include <string.h>
#include <malloc.h>

static void hdr(const char *name, void *p) {
    size_t *h = (size_t *)p - 2;                 /* prev_size, size */
    printf("  %-2s user=%p  prev_size=0x%04zx  size=0x%04zx  P=%zu\n",
           name, p, h[0], h[1], h[1] & 1);
}

int main(void) {
    setvbuf(stdout, NULL, _IONBF, 0);
    char *a = malloc(0x500), *b = malloc(0x500), *c = malloc(0x500);
    size_t usable = malloc_usable_size(a);
    memset(a, 'A', usable); memset(b, 'B', 0x500); memset(c, 'C', 0x500);

    printf("[1] malloc(0x500) -> chunk 0x510, malloc_usable_size(a) = 0x%zx\n", usable);
    hdr("a", a); hdr("b", b); hdr("c", c);

    free(b);                                     /* -> unsorted bin */
    puts("\n[2] after free(b): b is in the unsorted bin, c->prev_size was written");
    hdr("b", b); hdr("c", c);

    printf("\n[3] the bug: a[0x%zx] = 0   (one byte past a's usable space)\n", usable);
    a[usable] = 0;                               /* THE POISON NULL BYTE */

    void *d = malloc(0x4f0);                     /* make glibc touch b */

Three things to notice. (a) b.prev_size is full of 0x41 — proof that the last 8 usable bytes of a really are the next chunk’s prev_size slot. (b) One byte turned 0x511 into 0x500 and cleared P in a single stroke. (c) The naive version dies: modern glibc validates the phantom neighbour before using the chunk.

Step 2 — satisfy the checks plant a convincing fake header

/* b_chunk + 0x500 == b + 0x4f0 : where the phantom boundary points */
*(size_t *)(b + 0x4f0) = 0x500;   /* fake prev_size == the shrunken size  */
*(size_t *)(b + 0x4f8) = 0x20;    /* fake size: sane, and P = 0 because   */
                                  /* the chunk before it (b) is free      */

With a consistent fake header the unsorted-bin checks pass and glibc hands the shrunken chunk out. Get the fake size wrong and you learn which guard you tripped: 0x11 (P set) gives malloc(): invalid next->prev_inuse (unsorted); leaving garbage there gives malloc(): invalid next size (unsorted); a prev_size that does not match the size gives malloc(): mismatching next->prev_size (unsorted).

Step 3 — the payoff, and where 2.39 stops it

free(b1);
free(c);     /* P=0, prev_size=0x510 -> walk back and merge over b */
free(c)  -- tries to consolidate backwards over b ...
corrupted size vs. prev_size while consolidating
Aborted (core dumped)
On glibc 2.39 the shrink primitive still works, but the consolidation that produces overlapping chunks does not: before trusting prev_size, _int_free walks back and compares the real chunksize of the chunk it landed on with the prev_size it followed. 0x500 ≠ 0x510, abort. The attacker cannot fix that mismatch, because it lives in a header slot they do not control — which is exactly the point of the check.
This is why heap exploitation is written per libc version. On glibc ≤ 2.25 this chain runs end to end (that is poison_null_byte.c in how2heap). After the 2.26–2.29 hardening passes, poison-NULL-byte bugs are still exploitable in practice, but by paths that keep both size records consistent — House of Einherjar, large-bin and tcache-based variants — and usually with one more primitive (a leak, a second overflow, a UAF) in hand.

7 Not the same as tcache poisoning two different “poisons”

main mitigationsize-vs-prev_size consistency checks (2.26–2.29)safe-linking (glibc 2.32): the pointer is stored as ptr ^ (&ptr >> 12), so forging it needs a heap-address leak; plus the alignment check
They compose, which is why the names blur. A poison NULL byte that yields overlapping chunks gives you a write into a freed chunk — and the thing you then write is usually a tcache next pointer. Poison NULL byte is the entry; tcache poisoning is the exit.

8 Defence finding the byte before someone else does

Tools that catch off-by-one heap writes

Code rules that remove the bug class

  • malloc(strlen(s) + 1) — or strdup, which cannot get it wrong.
  • Prefer snprintf(buf, sizeof buf, …) over strcpy/strcat; never index with its return value without clamping.
  • Size arrays with sizeof at the point of use, not with a constant that can drift.
  • Keep length and buffer together in one struct, so “space left” is computed in one place.
  • Treat buf[n] = '\0' as a red flag in review: prove n < capacity, not n <= capacity.
For a defender the useful takeaway is the abort message as a diagnostic. corrupted size vs. prev_size in a production log is not a mysterious glibc bug — it is the allocator telling you that something wrote past the end of a heap buffer, probably by a very small amount. Reach for ASan, not for a retry loop.
