1The rule, and the 4 examples next to each other

Integer/pointer args 1–6 go in rdi, rsi, rdx, rcx, r8, r9. Arg 7 and up are pushed on the stack right-to-left, so arg 7 ends up at the lowest address: [rsp] right before the call, [rsp+8] once you're inside the callee (the return address is on top). The format string is arg 1, so only 5 of your ints fit in registers.

Why sub rsp,0x8 in the 8-arg version?

It is not a local variable. The ABI says rsp % 16 == 0 at the moment of every call. After push rbp main's rsp is aligned (…d690). Three pushes would add 24 bytes → …d678, misaligned. So gcc reserves 8 dead bytes first: 8 + 24 = 32 = 0x20 → …d670 ✓. That slot is never written; in the gdb run it still held 0x7fffffffd7b8 left over from before main.

Who cleans up?

The caller. printf doesn't know how many args you passed, so main undoes its own reservation with add rsp,0x20 (padding + 3 pushes). Then leave (= mov rsp,rbp; pop rbp) — gcc uses it whenever rsp moved inside the function; in the 3/4/5 versions rsp never moved, so a plain pop rbp is enough.

Why mov eax,0x0 before the call?

printf is variadic. For variadic calls al = how many vector registers (xmm0–xmm7) carry floating-point args. No doubles → 0. The mov eax,0x0 after the call is just return 0.

2Why are stack params pushed in reverse order?

C source order is f, g, h, but gcc emits push 0x8 (h) → push 0x7 (g) → push 0x6 (f). The stack grows down, so the last push lands at the lowest address. Pushing right-to-left therefore lays the args out in memory in source order, going up:

push order (time →) memory at the call ① push 0x8 ; h …d680 8 h [rsp+0x10] ② push 0x7 ; g …d678 7 g [rsp+0x08] ③ push 0x6 ; f …d670 6 f [rsp+0x00] ← rsp call printf …d668 ret ← rsp in printf first stack arg = closest to the return address, args ascend in memory in the same order as in C
// same printf, 32-bit cdecl (gcc -m32 -O0): NO arg registers, // all 9 args are pushed — still last → first push 0x8 ; h arg 9 push 0x7 ; g push 0x6 ; f push 0x5 ; e push 0x4 ; d push 0x3 ; c push 0x2 ; b push 0x1 ; a push 0x0 ; fmt arg 1 (reloc → "a=%d…") call printf add esp,0x30 ; 9×4 = 0x24 + 0xc padding

Why it has to be this way

  • Fixed offsets for the callee. Arg 7 is always at [rsp+0x8] on entry ([rbp+0x10] after the prologue), arg 8 always at +8 after that — no matter how many args were passed. If args were pushed left-to-right, the position of the first arg would depend on the total count.
  • Variadic functions need it. printf doesn't know how many args it got. It reads the format string (always in a known spot), then walks upward 8 bytes per %d. That only works if the first variadic arg is closest and the rest follow in order.
  • Caller cleans up (add rsp,0x20) for the same reason — only the caller knows how many bytes it pushed.
  • Register args are loaded in reverse too here (r9d first … esi last), but that's just gcc's habit; for registers the order of the movs doesn't matter.
  • Exploit angle: a format-string bug (printf(user_input)) uses the same walk — %6$p and above read straight up the caller's stack.

3The callee side — reserving room for locals and incoming params

The 4 mains above have no locals, so nothing is reserved for them. Here is what the callee does with its params and locals (same flags, gcc 10.5). At -O0 the register params are immediately spilled into the frame so they get a memory home like any local.

// leaf: calls nothing → no sub rsp int add(int x, int y) { int s = x + y; return s; } <add>: push rbp mov rbp,rsp ; ← no sub rsp! mov DWORD PTR [rbp-0x14],edi ; x (param) mov DWORD PTR [rbp-0x18],esi ; y (param) mov edx,DWORD PTR [rbp-0x14] mov eax,DWORD PTR [rbp-0x18] add eax,edx mov DWORD PTR [rbp-0x4],eax ; s (local) mov eax,DWORD PTR [rbp-0x4] pop rbp ret ; everything lives BELOW rsp → red zone (128 B)
// non-leaf: calls printf → must reserve int show(int x, int y) { int s = x + y; printf("%d\n", s); return s; } <show>: push rbp mov rbp,rsp sub rsp,0x20 ; reserve frame mov DWORD PTR [rbp-0x14],edi ; x (param) mov DWORD PTR [rbp-0x18],esi ; y (param) mov edx,DWORD PTR [rbp-0x14] mov eax,DWORD PTR [rbp-0x18] add eax,edx mov DWORD PTR [rbp-0x4],eax ; s (local) ... call printf@plt ; would overwrite the red zone mov eax,DWORD PTR [rbp-0x4] leave ret
  • Locals → [rbp-N], near rbp (s at -0x4). Spilled params → further down (x, y at -0x14, -0x18).
  • Leaf function: no sub rsp, it just uses the 128-byte red zone below rsp — nobody can clobber it because it calls nobody.
  • Non-leaf: sub rsp,N with N rounded up to a multiple of 16 (here 0x18 bytes used → 0x20), so the next call is aligned and the callee's pushes don't overwrite your locals.
  • Stack args from section 1 are on the caller's side of the return address: inside the callee they're [rbp+0x10], [rbp+0x18], … (positive offsets) — locals are negative offsets.
callee frame layout (rbp-based, -O0) [rbp+0x20] arg 9 ┐ [rbp+0x18] arg 8 │ pushed by the CALLER (only if > 6 args) [rbp+0x10] arg 7 ┘ [rbp+0x08] return address ← pushed by call [rbp+0x00] saved rbp ← push rbp ; mov rbp,rsp [rbp-0x04] locals ┐ ... spilled params │ reserved by sub rsp,N (or red zone if leaf) [rsp] ... ┘ rsp % 16 == 0 before the next call

takeaways

  • Args 1–6 → rdi rsi rdx rcx r8 r9; arg 7+ → pushed right-to-left; caller pops them (add rsp).
  • rsp % 16 == 0 at every call → odd number of stack args = 8 bytes of padding.
  • Arg registers are caller-saved: after the call, rdi…r9 may hold garbage. The args are gone unless you saved them.
  • Callee: locals at [rbp-N], stack args at [rbp+0x10+]; leaf → red zone, non-leaf → sub rsp,N.
