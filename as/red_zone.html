1What is the red zone?

The red zone is the 128 bytes just below rsp.
A function may use them without moving rsp. Nobody else will write there.

Think of rsp as a line on the floor. Everything above the line is the normal, "official" stack. The 128 bytes under the line are a small private area. The rules of the ABI promise that no one else (not a signal handler, not the kernel) will write there. So a function can use it as a free scratch pad.

This is the picture at step 8 of the stepper. local() stores both ints under rsp, and that is legal, because they are inside the 128 bytes.

2Why does it exist? Count the instructions

Normally a function must reserve space before it uses it: move rsp down, and later move it back. The red zone lets small functions skip both steps. Here is local() twice. On the left is the normal build. On the right, the red zone is switched off with gcc -O0 -mno-red-zone:

gcc -O0 (red zone on, the default on Linux):
local: push rbp mov rbp, rsp ; nothing here! mov DWORD PTR [rbp-0x4], 0xdad ; ↓ red zone mov DWORD PTR [rbp-0x8], 0xb00d ; ↓ red zone nop pop rbp ret
gcc -O0 -mno-red-zone (red zone off):
local: push rbp mov rbp, rsp sub rsp, 0x10 ; reserve 16 bytes mov DWORD PTR [rbp-0x4], 0xdad ; now above rsp mov DWORD PTR [rbp-0x8], 0xb00d nop leave ; = mov rsp,rbp + pop rbp ret

Same memory, same offsets. The only difference is the extra sub rsp and the leave that gives the space back. Thousands of small functions in a program each save that work, so the code is smaller and a little faster.

3When is a function allowed to use it?

SituationRed zone?Why
Leaf function: calls nothing, small locals✓ yes Nothing else runs on this stack while it works. local() is one.
Function that calls another function✗ not across the call call pushes a return address under rsp, right into the red zone. You saw it in step 4: main's red-zone row dae8 was overwritten.
Locals bigger than 128 bytes✗ not all of them The zone is only 128 bytes. Bigger frames need a real sub rsp, N.
Linux kernel code✗ no An interrupt pushes its data onto the current stack, under rsp. The kernel is built with -mno-red-zone.
Windows x64✗ no The Microsoft ABI has no red zone. It has shadow space instead: 32 bytes above the return address, reserved by the caller (see 006 vs 007).

"But a signal can come at any moment!"

True. A signal handler runs on the same stack, so it needs stack space too. The kernel knows about the red zone: when it delivers a signal, it first skips 128 bytes under rsp, and only then builds the signal frame. So the red zone survives. That is the "promise" of the ABI.

4See it yourself in gdb

Your old view.gdb printed only $rsp and up, so the two movs looked like they changed nothing. The new version also prints rows under rsp:

run main's prologue, the call, and both movs:
$ gcc -O0 main.c && gdb -q -x view.gdb ./a.out # break main stops at main+4 (gdb skips the prologue) (gdb) stepi 6 (gdb) x/gx $rsp-8 0x7fffffffdad8: 0x00000dad0000b00d (gdb) x/2wx $rbp-8 0x7fffffffdad8: 0x0000b00d 0x00000dad var_b ↑ var_a ↑
the stack part of the new view.gdb:
0x7fffffffdaf8: 0x7ffff7df9d7a <__libc_start_main+234> 0x7fffffffdaf0: 0x555555555150 <__libc_csu_init> 0x7fffffffdae8: 0x555555555148 <main+14> 0x7fffffffdae0: 0x7fffffffdaf0 <------- rsp -------- below rsp (red zone) -------- 0x7fffffffdad8: 0xdad0000b00d 0x7fffffffdad0: …

Why do two ints look like one number? Both live in the same 8-byte row. x86 is little-endian: the lowest address holds the lowest byte. var_b is at dad8 (low half), var_a at dadc (high half). So x/gx prints var_a's digits first.

Takeaways

  • The red zone = the 128 bytes under rsp (rsp−0x80 … rsp−1). It moves when rsp moves.
  • Leaf functions put small locals there without sub rsp. In a listing: push rbp / mov rbp,rsp, then [rbp−X] writes with no sub rsp in between.
  • Data under rsp is real data. When you debug, look below rsp too.
  • Linux / macOS user space only (System V ABI). Not in the kernel, not on Windows.
